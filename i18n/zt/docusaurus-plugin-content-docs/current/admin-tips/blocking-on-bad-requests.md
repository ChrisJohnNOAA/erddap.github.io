# 屏蔽 ERDDAP™ 根據要求的內容而不是IP

此內容基于 [羅伊·門德爾索恩致 ERDDAP™ 使用者群組](https://groups.google.com/g/erddap/c/XcvPkoGtchg) .

## 問題

如果你像我們一樣,你看到很多 bots在向您的數據要求 ERDDAP™ ,而這些要求往往似乎都是由編碼不良的文稿完成的,不管是LLMS (我猜) 或由人類。 關於LLMS的一件事是, 他們會做你激勵他們做的事, 所以如果你不告訴他們要檢查腳本回碼, 如果你告訴它繼續試,它會的。 我們至少看到了這些

但那些在我們身上做數字的人 ERDDAP™ 就像這樣:

 https://coastwatch.pfeg.noaa.gov/erddap/jplMURSST41.parquetWMeta
 

這些寄件者 ERDDAP™ 網址不僅要求整個數據集, 也就是我不知道有多少百兆字節, 更糟糕的是,從移動的IP中傳來的要求, 所以封鎖IP比傻子還糟糕, 你永遠不會被封鎖。

所以問題是,你怎麼能根據要求的內容阻擋? 在繼續前, 如果你是經驗撞擊, 可能是不同原因造成的, 那麼我們所看到的, 我花了很多時間經過紀錄, 在任何行動前先研究一下 但這可能會讓你知道如何阻止這些要求

我很清楚,你可以想到 ERDDAP™ 要求如下:

 https://baseURL/erddap/method/datasetID.filetype?constraint
 

就我們而言, 撞擊的共同分母是 格格達普或桌面要求, 有某些檔案型態, 但沒有限制 。 所以問題是如何不受限制地阻止要求? 因為有許多檔案型態不需要限制, 在跟克裡斯談完後 我肯定漏掉了一些東西 檔案型態的行為很順利

- .croissant( . )
- .iso19115_2
- .iso19139_2007
- .iso19115_3_2016
-  .nc CF 页眉
-  .nc CFMA 信头
- .das
- .dds
- .html
- 圖片
- . 子集
-  .nc 信頭
- 幫助
- .fgdc
- .iso19115
-  .nc oJson 信頭 (這個將在將來的新版中) .

## 解决办法

「我找到了」的解答在Apache2工作, 起初我試過mod_security, 但這變得太複雜, 解答是使用mod_rew 。 現在我只不過是專家 所以當我說清楚我試圖完成的任務時 解決辦法和解釋 都怪克勞德 知乎. ChatGPT會給你提供基本相同的答案.

第1步. 确定mod_rew已安裝并啟用 。 如何做和OS不同 這是你最喜歡的聊天人

第 2 步 。 (它又因OS而變化) 例如,它可能是像 /etc/apache2/sites-uplied/ssl.conf 一樣,在相當的虛擬Host定義下加入以下 (注意,如果你复制了這個, 只有4行, 第三行可能會被包起來, 解開它) 

```
RewriteEngine On
RewriteCond %{QUERY_STRING} ^$
RewriteCond %{REQUEST_URI} ^/erddap/(griddap|tabledap)/[^/?]+\\.(?!(?:croissant|iso19115_2|iso19139_2007|iso19115_3_2016|ncCFHeader|ncCFMAHeader|das|dds|html|graph|subset|ncHeader|help|fgdc|iso19115|ncoJsonHeader)$)[A-Za-z0-9_]+$
RewriteRule ^ - [R=429,L]
```

第三步 檢查配置是否合法 : `sudo apache2ctl 設定測試` 

步 4. 恢复阿帕切2: `sudo systemctl 重新啟動 apache2` 

第五步 檢查您的紀錄, 沒有什麼被封鎖的 不該封鎖的 , 而且沒有限制的 適當的請求 。 。

## 解釋

為何這項工作,

第1行—— `重寫引擎 開啟` 
開啟此範圍的mod_ 重寫處理 。 沒有它, 下面的 RewriteCond / Rewrite Rules 指令就會被忽略 。

第2行 - `重寫已編寫的 $` 
這條條件必須是真實的, `(Y: 我)` 之后的一切? 。 ^$ 是 regex 的意思, 意思是「 立即開始字串, 接著結束字串」 , 也就是空字串 。 所以這個條件只有在完全沒有查詢字串時才是真的——在要求上沒有子設定/约束表示.

第3行—— `重寫 Cond &#123;REQLEST_URI&#125;\\/erddap/ (网格 |  tabledap ) /[^/?]+\\. (&#33; (:) $) [A-Za-z0-9_]+美元` 
第二條件,檢查一下 `(請求)` ─ 客戶端傳送的字面要求路徑, 總是完整路徑, 不管此規則在配置中住在哪裡 。 (故意選擇讓 Rewrite 規則樣式自己來做配對, 因為樣式比對內部 ` <Location> ` 區塊可以模棱两可的行為,) . 打破正規 :

 `^/erddap/ (%)` ─必須從/erddap/開始
 (网格 |  tabledap ) /- 之后是其中之一 ERDDAP™ 存取方法

 `[^/?]+` —— datasetID : 一個或多個不是 / 或 ?

 `~.` 字面點

 ` (&#33; (? : croisant ? | 等於19115_2 | ... | ncoJson 信頭) $) ` 反面看頭:"只要以下的不是這些文件之一 一直打到字串的末端。" 這些是檔案 Types ERDDAP™ 合法服役 (元数据、 結構、 窗体頁面等) 眼界是他們不被阻擋的原因

 `[A-Za-z0-9_]+美元` ——真正的檔案 型態延伸 (字母、 數字、 下划線) ,需要執行到字串的末端。
所以只有路徑是網格dap/時,此條件才是真的 tabledap 要求一些檔案 沒有安全限制的型態

第4行—— `重寫 ^ - [R=429, L]` 
規矩本身 因為以上兩條條條件對阿帕奇來說都已經是真的, - 意思是"不要把網址重寫到任何不同的" (我們沒有轉移到任何地方, 只是短路要求) . 旗:

 `R=429` 以 HTTP 重定向群組的狀態代碼 429 做回應 ("太多的要求") 而不是服從要求。
L ─ "最后" : 停止處理任何进一步的重寫規則, 一旦這一次發射。
拼合: 如果查詢字串是空的, 而要求的是 gradap/ tabledap 文件 安全無限的類型, 立即傳回429, ERDDAP Tomcat后端。

為什麼 `(請求)` 而不是讓规则模式直接符合路徑 (值得作為同事的注解 因為這不明顯) : 內置 a ` <Location> ` 區塊, 赤裸的 Rewrite 規則模式實際上得到的匹配 。 透過 RewriteCond 明确拉動整條路徑 `(請求)` 所以regex的行為與文字完全一致,


我已使用數天, 似乎效果很好, 它阻擋了我試圖阻擋的東西, 我們的 ERDDAP™ 越來越穩定了
